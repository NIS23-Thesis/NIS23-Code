# CLIVE Event Stream and MANET map — developer guide

This is a **read-only visualizer**. It does not advance protocol timers and does not modify FLAME's packet formats, packet serialization, fragmentation, reliability, routing, training or neighboring modules.

## Three views (one selector; one search field)

- **FLAME activity** (default): meaningful actions like `flame_hello_sent`, `flame_ch_discovered`, `flame_join_sent`, `flame_joined`, `flame_trained`, `flame_aggregated`, `flame_model_received`, `flame_transfer_failed`, `flame_leave_sent`, `flame_connection_lost`. Internal reassembly/queue housekeeping is omitted from this view to reduce noise.
- **FLAME packets sent**: the actual `transmit` events from CLIVE's NodeSocket with decoded FLAME packet type and sequence number, plus `local_drop` when a send is dropped before transmission. One data fragment can be a separate wire packet; packet transmission does not prove FLAME application acceptance.
- **CLIVE network**: transport `transmit`, `receive`, `delivery_drop`, `local_drop`, `socket_error` events. These show what the emulated radio/NodeSocket did, not changes in FLAME membership.

A packet sequence number is *not* an Event Stream record ID. Training and aggregation are local actions and need not carry a packet sequence number. The actual FLAME protocol `sequence_number` is shown when it was logged. An event's `trigger_sequence_number` identifies a causal packet (if available), not an outgoing packet generated by that action.

The map and event feed use the time selected in **playback**, not current wall-clock time. The live list is a **last-8-second preview** capped at 160 recent matching events; the summary reports the matching count. **Open complete recorded history** for paginated access to every *recorded* event. **See failures only** opens that archive with failures selected. Missing logs cannot be reconstructed.

## Map activity

In the default **FLAME protocol** view, current observed associations remain lines. Additional labels are **transient observations** for HELLO, JOIN, model transfers, training/aggregation, and LEAVE/timeout. A CH HELLO broadcast is drawn as a pulse around its sender; a sensor's reception of a HELLO is shown as a temporary discovery arrow. A LEAVE or recorded timeout appears as a red dashed indication for a short interval, not a permanent connection. The display shows at most seven distinct recent signals in a 2.2-second window to avoid clutter; it does not fabricate missing events or infer JOIN from radio reachability.

CH-to-CH model links aren't permanent: an old exchange is only shown as recent activity for three seconds. Candidate CH radio links and selected-node candidate links are **off by default**; enable them under Layers when investigating radio possibilities. The Node Inspector retains actual recorded membership and connection history.

## Files

| File | Responsibility |
|---|---|
| `clive/visualizer.py` | Normalize logged event fields, filter and page indexed on-disk event logs, emit observed protocol history |
| `clive/visualizer/static/event_stream.js` | Describe events, distinguish packet sequence from event IDs, render safe human-readable rows |
| `clive/visualizer/static/map_activity.js` | Select and label a bounded set of recent actual protocol signals for the map |
| `clive/visualizer/static/app.js` | Query playback window and draw topology, packet markers and event rows |
| `clive/visualizer/static/events.js` | Full archive page and packet-name search |
| `clive/validation/validate_simple_event_map.py` | Backend tests for categories, search and map event provenance |
| `clive/validation/validate_simple_event_map_js.js` | Frontend tests for event categorization and map signals |

## Test locally

From the `clive/` directory:

```bash
python validation/validate_simple_event_map.py
node validation/validate_simple_event_map_js.js
python validation/run_all.py
```

Run the root `./start_gui.sh` to launch a demo and open the Network Map. Select **Events** and use the three choices in **View**. If protocol events or packet logs were disabled for a run, those historical records cannot be reconstructed.

## Known boundaries

- An ACK confirms a transport/protocol condition only when FLAME records the corresponding event. A CLIVE RX does not prove the complete fragmented message was accepted.
- Events are read from the output files; the map is not a reliable live network-state oracle.
- FLAME's underlying ACK-window/retransmission defects remain untouched.
- The protocol's first-compatible-HELLO association policy, as shipped in the base ZIP, remains unchanged.
